# Development

Python 3 standard library only — no Flask, no pip packages, no build step.
Keep it that way: the target is a Raspberry Pi Zero W running the distro's
Python (3.9 on Bullseye).

## Running the tests

```bash
python3 -m unittest discover -s tests -v
```

The tests run on any machine (Linux, macOS, CI) — nothing touches `/etc`, no
port is bound and every system command is stubbed:

| File | Covers |
|---|---|
| `tests/test_store.py` | store writes (PSK hashing = `wpa_passphrase`, 0600, tri-state home flag, forget) |
| `tests/test_daemon_confs.py` | generated `wpa_supplicant.conf` (priorities, escaping, no duplication, foreign head kept), dnsmasq conf, uptime/clock-step logging |
| `tests/test_http.py` | the config server over a socketpair: captive redirect, Host/Origin guards, page rendering + escaping, `/api/status`, shutdown |
| `tests/test_naming.py` | device name, AP SSID (32-byte limit), setup domain |

`tests/support.py` points every path at a temp directory **before** the
modules are imported (they read their configuration at import time) — import it
first in new test files.

Other quick checks:

```bash
python3 -m py_compile wifi_setup_daemon.py wifi_config_server.py wifi_scan.py
bash -n wifi_setup.sh
node --check static/app.js        # or: deno check static/app.js
```

### Running the setup page locally

The HTTP layer runs on a normal computer (the system calls behind it are
Linux/root-only and fail gracefully):

```bash
mkdir -p /tmp/ws
WIFI_CFG_DIR=/tmp/ws WIFI_WPA_CONF=/tmp/ws/wpa.conf WIFI_CONFIG_HOST=127.0.0.1 \
  WIFI_DEVICE_NAME=Demo python3 wifi_config_server.py 8901
# http://127.0.0.1:8901/
```

Don't press *Shutdown* or *Save & reboot* on a Linux machine where you are root.

### Rules worth keeping

- `known-wifi.json` is the only store; every mutation goes through
  `write_store()` in `wifi_config_server.py` (atomic replace, 0600).
- hostapd/dnsmasq/wpa_supplicant confs are generated by the daemon — don't add
  templates for them.
- The config server binds only to the AP address, never `0.0.0.0`; keep the
  Host/Origin checks on every route.
- `config/known-wifi.json` stays empty in the repository.

## Updating a device you can only reach over WiFi

A Pi Zero W has no Ethernet port; in the field SSH usually rides on `wlan0`.
**Every restart of the service, every save and entering setup mode drops that
link.** A device that ends up with neither a client link nor a setup AP needs
physical access. So:

1. **Verify off-device first** (tests above). The device is the worst place to
   find a syntax error.
2. **Look before you touch** — `iwgetid -r`, `sudo tail -n 80
   /etc/wifi-setup/daemon.log`. A restart regenerates the conf and destroys the
   evidence.
3. **Back up** what cannot be recreated:
   ```bash
   sudo cp /etc/wifi-setup/known-wifi.json ~/known-wifi.json.bak
   sudo cp /etc/wpa_supplicant/wpa_supplicant.conf ~/wpa_supplicant.conf.bak
   ```
4. **Arm a rescue before the restart.** It survives the dropped SSH session
   and restarts the daemon two minutes later, which recovers from any radio state
   (conf regenerated, one wpa_supplicant started, all networks enabled):
   ```bash
   sudo systemd-run --on-active=120 --unit=wifi-setup-rescue \
     /bin/sh -c 'systemctl restart wifi-setup'
   ```
   It re-runs the *same* code, so it helps with hangs and one-off states, not
   with a bug that fails on every start — that is what step 1 is for. A stray
   fire is harmless (a clean restart, ~15 s offline).
5. **Transfer and install** — `scp -r` the folder, then
   `sudo bash wifi_setup.sh` (idempotent; keeps store and env file). UI-only
   changes (`templates/`, `static/`) can simply be copied into
   `/opt/wifi-setup/` without a restart.
6. **Restart detached and read afterwards** — never `tail -f` across the
   restart, your session dies with the link:
   ```bash
   sudo systemctl restart wifi-setup ; exit
   # reconnect after ~1-2 min
   sudo tail -n 60 /etc/wifi-setup/daemon.log
   ```
7. **Keep a known-good network in range** until the device is back on it.

If the link does drop: the supervisor self-heals after ~20 s and opens the setup
AP after the setup timeout (plus a pre-AP scan of up to two minutes). Join
`<hostname>-Setup` and `ssh pi@192.168.4.1`.

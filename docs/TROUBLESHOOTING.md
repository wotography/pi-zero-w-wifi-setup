# Troubleshooting

> **Read before you restart.** Restarting the service regenerates
> `wpa_supplicant.conf` from the store — whatever state you wanted to inspect
> is gone afterwards. Look first, restart second.

## Quick health check

```bash
systemctl is-active wifi-setup                       # the supervisor
sudo tail -n 80 /etc/wifi-setup/daemon.log            # what it did and why
iwgetid -r                                            # current network (empty = none)
sudo iw dev wlan0 info                                # "type managed" = client, "type AP" = setup mode
sudo python3 /opt/wifi-setup/wifi_setup_daemon.py --diagnose --redact
```

`--diagnose` is read-only: stored vs. generated credentials per network, the
effective `priority=`, live `wpa_cli status`, country and a fresh scan. It needs
`sudo` (store and confs are root-only). Use `--redact` before sharing the output:
a 64-hex `psk=` **is** the WPA2 key.

## Reading the log

- `[up H:MM:SS]` on every line is the time since boot. Right after a power cut
  the wall-clock timestamps can be wrong (no RTC); a *Boot reference* line at
  start and a *Wall clock stepped by ±Ns* line when NTP corrects the clock tell
  you by how much. Build timelines across a reboot from `[up …]` and `boot_id`
  (`journalctl --list-boots`), not from the wall clock.
- WARNING lines mark state changes (link lost, setup mode, AP problems) and are
  written immediately; INFO lines may lag by about a second.

## Symptoms

### The device does not connect to a network it should know

```bash
sudo wpa_cli -i wlan0 list_networks                                   # every saved network listed?
sudo grep -n 'disabled=1' /etc/wpa_supplicant/wpa_supplicant.conf     # must print nothing
sudo grep -n 'priority=' /etc/wpa_supplicant/wpa_supplicant.conf      # home network 10, others 1
```

A `disabled=1` means wpa_supplicant will only try one network. Immediate
unblock: `sudo wpa_cli -i wlan0 enable_network all && sudo wpa_cli -i wlan0
reassociate`. It should never appear in a conf generated by wifi-setup — if it
does, something else rewrote the file.

### It joins the "wrong" network

When several saved networks are in range and none is the home network,
wpa_supplicant picks the strongest one. Mark the one you want with ★ on the
setup page (or `"preferred": true` in the store) and reconnect.

### Associates, then drops after a few seconds

Compare the stored key with the real passphrase:

```bash
sudo python3 /opt/wifi-setup/wifi_setup_daemon.py --diagnose    # psk per network
wpa_passphrase '<ssid>' '<real password>'                       # what it should be
```

Different hashes → wrong credential stored; save the network again on the setup
page. Identical hashes → a timing or router issue: the log records each sample
of a live switch (`wpa_state=SCANNING → ASSOCIATING → 4WAY_HANDSHAKE →
COMPLETED`, then DHCP). A loop in `4WAY_HANDSHAKE`/`ASSOCIATING` with a correct
key points at the router.

### The setup AP does not appear

- It is **slow, not absent**: after the timeout the daemon first stops
  wpa_supplicant and scans (several retries, up to about two minutes on a Pi Zero
  W) before `hostapd` starts. During that window there is neither a client link
  nor an AP.
- Check `systemctl status hostapd dnsmasq` and the log: the daemon logs the
  journal of a service that failed to start. After three failed attempts it
  returns to client mode and tries again at the next outage.

### The setup AP rejects the correct password

The AP password must be **8–63 printable ASCII characters**. Characters such as
`€` or umlauts are not defined for WPA2: hostapd accepts them, but many phones
refuse the input or compute a different key. The daemon logs a WARNING at start
when `WIFI_AP_PASSWORD` breaks this rule. Fix it in
`/etc/wifi-setup/wifi-setup.env` and restart the service (it drops a WiFi SSH
session — see [DEVELOPMENT.md](DEVELOPMENT.md#updating-a-device-you-can-only-reach-over-wifi)).

Also remember that a saved WiFi entry on the phone is bound to the AP *name*:
after the device was renamed, the password has to be entered again.

### The setup page does not open by itself

- Browse to `http://192.168.4.1` directly.
- The phone must stay on the setup WiFi: on iOS don't cancel the sign-in window
  (*Use Other Network → Use Without Internet*); Android may offer to switch to
  mobile data — decline.
- `WIFI_CAPTIVE_PORTAL=0` disables the automatic pop-up.

### Phone gets no IP address on the setup AP

`dnsmasq` is not running (`systemctl status dnsmasq`). As a stop-gap, give the
phone a static IP like `192.168.4.50/24`, gateway `192.168.4.1`, then open the
page or `ssh pi@192.168.4.1`.

## Getting back into a device you can only reach over WiFi

While the setup AP is up you can always `ssh pi@192.168.4.1` from a device
joined to it — `sshd` does not care whether `wlan0` is a client or an AP.

If the device has neither a client link nor an AP, wait: the supervisor
self-heals after ~20 s and opens the AP after the setup timeout. A device that
stays unreachable needs physical access (power cycle, or the SD card in another
computer: the store is `/etc/wifi-setup/known-wifi.json`). Before doing anything
risky remotely, see
[DEVELOPMENT.md](DEVELOPMENT.md#updating-a-device-you-can-only-reach-over-wifi).

## Rollback

```bash
sudo systemctl disable --now wifi-setup
sudo cp ~/wpa_supplicant.conf.bak /etc/wpa_supplicant/wpa_supplicant.conf
sudo reboot
```

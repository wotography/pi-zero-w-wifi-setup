# How wifi-setup works

## Components

```
wifi_setup.sh            one-shot installer (root): packages, files, unit, env file
wifi_setup_daemon.py     supervisor (systemd service `wifi-setup`)
wifi_config_server.py    stdlib http.server setup page + JSON API (child of the daemon)
wifi_scan.py             shared helpers: scanning, scan cache, device naming
templates/, static/      the single-page UI
systemd/wifi-setup.service
config/known-wifi.json   optional seed store (ships empty)
```

Installed to `/opt/wifi-setup`. Runtime state in `/etc/wifi-setup/`:
`known-wifi.json` (store), `wifi-setup.env` (settings), `daemon.log` (+ one
rotated `.1`), `daemon.pid`, `scan-cache.json`, `connect-state.json`,
`config-cert.pem` / `config-key.pem`.

Generated by the daemon at runtime (never shipped as templates):
`/etc/wpa_supplicant/wpa_supplicant.conf` (+ `wpa_supplicant-wlan0.conf`),
`/etc/hostapd/hostapd.conf`, `/etc/dnsmasq.d/wifi-setup.conf`.

## Lifecycle

1. **Start.** Resume a `dhcpcd` left paused by a crash, stop any leftover
   `hostapd`/`dnsmasq`, flush stale `wlan0` addresses, then regenerate the
   wpa_supplicant conf from the store and attach exactly one wpa_supplicant.
2. **Connect window** (`WIFI_CONNECT_TIMEOUT`, 90 s). Connected → supervise.
   Not connected → setup mode.
3. **Supervise.** wpa_supplicant handles reconnects itself; the daemon only
   watches. When the link drops it fires **one** self-heal (`enable_network
   all` + `reassociate`, restarting wpa_supplicant if its socket is gone) about
   a third into `WIFI_SETUP_TIMEOUT` (60 s), so any other saved network in range
   is tried before the user is bothered. Still down after the timeout → setup
   mode, live, no reboot.
4. **Setup mode.** Scan once in client mode and cache the result (the Pi Zero
   W's `brcmfmac` cannot scan while it is an AP), pause `dhcpcd`, start
   `hostapd` + `dnsmasq` on `192.168.4.1`, spawn the config server. It ends when
   a live switch succeeds, the user leaves setup mode, or `wlan0` is back
   online. The config server tells the daemon what to do through a small state
   file (`connect-state.json`).

## Design decisions

### `wpa_supplicant.conf` is generated, and `select_network` is undone

`known-wifi.json` is the only source of truth. The conf is regenerated on every
start and every save, always *after* all wpa_supplicant instances have been
stopped (a running instance could otherwise write its own state back on exit).
The generated head forces `update_config=0`.

`wpa_cli select_network <id>` — used by *Save & connect* to switch right away —
disables every *other* network and turns off auto-reconnect. The live switch
therefore always ends with `enable_network all`, and with `update_config=0`
that transient state can never reach disk. A conf containing `disabled=1` is a
bug fingerprint.

### The home network is a preference, not a pin

Without `priority=`, wpa_supplicant joins the **strongest** BSSID among all
enabled networks. With two overlapping networks of similar strength that is a
coin flip, and the device may end up on a network where the services it needs
are not reachable. One store entry can therefore carry `"preferred": true`; the
generator writes `priority=10` for it and `priority=1` for all others.
wpa_supplicant orders by priority and only uses signal strength within a level.

It never disables anything: with the home network out of range the others are
used as before. The flag is a stored boolean; the numbers exist only in the
generated conf. `wpa_cli list_networks` does not show priorities — use
`--diagnose`.

### One wpa_supplicant, one owner of `wlan0`

`hostapd` and wpa_supplicant cannot both own `wlan0`. Before any attach the
daemon stops every wpa_supplicant, makes sure `/var/run/wpa_supplicant` exists
(it lives on tmpfs and is missing on some minimal images), then starts exactly
one instance and verifies it answers `PING`: the per-interface
`wpa_supplicant@wlan0` unit if enabled (the installer enables it), else the
monolithic service, else a direct `wpa_supplicant -B`.

`hostapd`/`dnsmasq` are only ever started and stopped explicitly — never
enabled or disabled at runtime. `dhcpcd` is paused while the AP is up (it would
re-DHCP `wlan0` and steal the static AP address) and restored afterwards; a
marker file makes this survive a crash.

### "Connected" is hard to fake

Connected = IPv4 on `wlan0` **and** `wpa_state=COMPLETED` **and** (a default
route via `wlan0` **or** working DNS). An address or route left behind after a
dropped association therefore cannot make the daemon believe it is online
forever. No gateway ping (some routers drop ICMP).

### The setup AP is verified, and giving up is not a dead end

After starting `dnsmasq` and `hostapd` the daemon checks that both are active
(retrying once and logging their journal otherwise) and that `wlan0` really is
in AP mode. If the AP fails `WIFI_AP_FAIL_LIMIT` (3) times in a row, the daemon
hands `wlan0` back to wpa_supplicant and keeps supervising — the next outage
tries the AP again. The dnsmasq conf uses `bind-dynamic` (dnsmasq 2.86+ fails
if `bind-interfaces` is combined with it) and `dhcp-authoritative`.

### Captive portal

dnsmasq answers every name with `192.168.4.1`, so the phone's connectivity
probe (`captive.apple.com`, `connectivitycheck.gstatic.com`, …) reaches the
config server. A `GET` for a foreign host gets a `302` to the page — never page
content or API data — so the DNS-rebinding guard still holds; foreign-host or
foreign-origin `POST`s get `403`. With HTTPS active, a plain-HTTP listener on
port 80 sends probes to `https://192.168.4.1/`. No DHCP option 114 (RFC 8910):
iOS would expect an RFC 8908 JSON API behind it. The captive sheet on macOS/iOS
suppresses `window.confirm()`, so the page uses its own confirmation dialog.

### Answer first, then switch

The setup page reaches the device *through* the AP that a save tears down. Every
action that drops the AP (*Save & connect*, *Save & reboot*, *Rescan*, *Leave
setup mode*, *Shutdown*) sends its response — including the log tail — before
it acts. *Save & connect* never reboots on its own; *Save & reboot* is the
explicit robust path.

### Open AP powers off

A password-less setup AP is kept for `WIFI_AP_AUTO_OFF_SECONDS` (15 min, the
page shows a countdown), then the device powers off. A secured AP stays up — the
device would otherwise be unreachable.

### Logging that survives power cuts and a missing clock

`daemon.log` is read by the page (`/api/log`). The daemon writes it through a
buffered, size-rotating handler (1 MB + one backup): WARNING and above flush
immediately, INFO within about a second, an idle buffer causes no I/O — light
on the SD card, and the periodic flush (not exit handlers) is the power-loss
safety net.

The Pi has no RTC: after a power cut the clock resumes from the last saved time
and is wrong until NTP syncs. The daemon does **not** wait for a synced clock —
NTP needs the network the daemon is responsible for bringing up. Instead every
line carries `[up H:MM:SS]` (monotonic, never stepped), a *Boot reference* line
records boot time, uptime, `boot_id` and NTP state at start, and a
*Wall clock stepped by ±Ns* line marks the moment NTP corrects the clock.

## Limitations

- dhcpcd + wpa_supplicant only (Raspberry Pi OS Bullseye/Legacy); not
  NetworkManager.
- WPA2-PSK and open networks only; no WPA-Enterprise (802.1X).
- Single radio: while the setup AP is up the device has no client connection.
- *Save & connect* (AP → client without reboot) is best-effort on `brcmfmac`;
  *Save & reboot* is the reliable fallback.
